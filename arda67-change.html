ARDA67 API: สรุปการเปลี่ยนแปลง

รอบนี้เน้นแก้ช่องโหว่และ bug ในหลังบ้าน โดยไม่เปลี่ยน URL หรือรูปแบบ response ของ /v1 และเพิ่ม /v2 สำหรับ 6 module ที่ทำ path ใหม่เป็นแบบ REST ให้ย้ายไปใช้เมื่อพร้อม

ไม่ต้องแก้

/v1 ใช้ได้เหมือนเดิม

URL, parameter, ชื่อ field และรูปแบบ {code, result, error} เหมือนเดิมทั้งหมด token เดิมก็ยังใช้ได้

ต้องเช็ค

มีกรณีใหม่ที่ได้ 403

แก้หรือลบข้อมูลของคนอื่น และใช้เส้น admin โดยที่ไม่ใช่ admin จะถูกปฏิเสธ ควรเช็คว่า UI แสดงข้อความ error ได้

plang, subplang, activity, disaster, alert, community ใช้ id ใน path, ตรวจข้อมูลก่อนบันทึก และตอบ HTTP status ตรงกับ code

1. สิ่งที่เปลี่ยนใน /v1

1.3 POST /v1/user/user_detail

  • เพิ่ม role ตั้งแต่ 3 ขึ้นไปให้ตัวเองไม่ได้แล้ว (เดิมเกษตรกรตั้งตัวเองเป็น admin ได้) จะได้ 403 พร้อมข้อความ "ไม่สามารถเพิ่ม role … ให้ตัวเองได้" ส่วน role 1 และ 2 ยังเปลี่ยนเองได้ และ role ที่มีอยู่แล้วส่งค่าเดิมกลับมาได้ตามปกติ
  • ค่า star_farmer ที่ส่งมาจะถูกข้าม ถ้าผู้ส่งไม่ใช่ role 3 ขึ้นไป (ให้ใช้ /v1/user/star_farmer แทน)
  • ถ้าไม่ส่ง user_role มา ระบบจะใช้ role เดิม (เดิม request จะ error)

1.4 รูปแบบ error

  • error จากฐานข้อมูล: error จะเป็นข้อความ "เกิดข้อผิดพลาดภายในระบบ กรุณาลองใหม่อีกครั้ง" แทน object ของ MySQL เดิม (ที่มี sqlMessage, code) HTTP status ยังเป็น 400 เหมือนเดิม ถ้าโค้ดฝั่ง front end อ่าน error.sqlMessage หรือ error.code ต้องแก้
  • เรียก URL ที่ไม่มีอยู่ จะได้ JSON {"code":404,…} แทนหน้า HTML
  • header ตอบกลับเปลี่ยนจาก text/json เป็น application/json (axios และ fetch อ่านได้เหมือนเดิม)
// ตัวอย่าง 403
{ "code": 403, "result": null, "error": "ไม่มีสิทธิ์แก้ไขข้อมูลนี้ (plang: 12)" }

1.5 Bug ที่แก้แล้ว (ไม่ต้องทำอะไร)

  • GET /v1/action/master ใช้ได้แล้ว (เดิมเส้น /:action_id ดักไว้ก่อน ทำให้ได้ action_id = "master")
  • upload รูป: ระบบจะรอให้เขียนไฟล์เสร็จก่อนบันทึก path ถ้าเขียนไฟล์ไม่สำเร็จจะตอบ error (เดิมตอบสำเร็จแต่ไม่มีไฟล์จริง)
  • register: รอ INSERT เสร็จก่อนออก token

2. /v2 (ใหม่)

/v2 มีเฉพาะ plang, subplang, activity, disaster, alert, community ส่วน auth, user, admin, action, forecast และ report ให้ใช้ /v1 ต่อไป ใช้ token เดียวกัน (Authorization: Bearer <refreshToken จาก /v1/auth/login>) และ logic หลังบ้านเป็นชุดเดียวกับ v1 ผลลัพธ์จึงเหมือนกัน

2.2 ตรวจข้อมูลก่อนบันทึก

v2 ตรวจชนิดข้อมูลก่อนส่งเข้าฐานข้อมูล เช่น id ต้องเป็นตัวเลข, ไร่/งาน/วา ต้องเป็นตัวเลข (ส่งเป็น string ตัวเลขได้), วันที่ต้องอ่านได้ และ parent id ที่จำเป็นต้องส่ง ถ้าไม่ผ่านจะตอบ 400 พร้อมรายการ field ที่ผิดใน result

{
  "code": 400,
  "result": ["body.rai: ต้องเป็นตัวเลข", "body.plang_id: จำเป็นต้องส่งค่านี้"],
  "error": "ข้อมูลไม่ถูกต้อง"
}

3. สิ่งที่ยังไม่เปลี่ยน

  • login, register และ token: ยังใช้ refreshToken จาก /v1/auth/login เป็น Bearer token เหมือนเดิม และอายุ token ยังเป็น 100 วัน (การทำ access/refresh token แยกกันจะคุยกันอีกรอบ เพราะฝั่ง front end ต้องทำ flow ขอ token ใหม่)
  • ชื่อ field ใน result ของทุกเส้นเหมือนเดิม
  • สำหรับ "ไม่พบข้อมูล" ยังตอบ HTTP 200 พร้อม code: 204 ทั้ง v1 และ v2
  • เอกสาร API อยู่ที่ /docs เหมือนเดิม ตอนนี้กดปุ่ม Authorize แล้วใส่ token ครั้งเดียวก็ทดสอบได้ทุกเส้น และค้นหาเส้นด้วยช่อง filter ได้

4. Checklist สำหรับทีม front end

  • หน้าแก้ไข/ลบข้อมูลแปลง แสดงข้อความเมื่อได้ code: 403
  • มีหน้าไหนที่ role อื่นนอกจาก admin เรียก /v1/admin/… หรือไม่ (นอกจาก /roles) ถ้ามี แจ้ง backend ให้เปิดสิทธิ์
  • หน้าแก้ไขโปรไฟล์ส่ง user_role เป็น role เดิมของ user (ไม่เพิ่ม role ใหม่ตั้งแต่ 3 ขึ้นไป)
  • ไม่มีโค้ดอ่าน error.sqlMessage หรือ error.code จาก response
  • ถ้ามีอุปกรณ์หรือบัญชีกลางที่ส่ง soil meter แทนเกษตรกร: ตอนนี้ยังไม่ตรวจสิทธิ์เส้นนี้ แจ้ง backend ถ้าควรตรวจ
  • ทดลองย้ายไป /v2 ทีละ module ได้เลย (ใช้คู่กับ /v1 ได้)
